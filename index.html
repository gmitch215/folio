    🚋 Folio

    ⚡ WebAssembly tooling for Node, Workers and browsers

    Folio is a toolkit for running, resetting and bounding WebAssembly modules in JavaScript runtimes. Its core runs native WebAssembly across several V8 isolates that share one physical memory allocation. It finds inline memory regions and pure calls in ordinary programs, validates the ones it cannot prove independent, and keeps the serial result. Around the core sit task and slice pools, exact stream folds, instance checkpoints, baked boot images, a growth governor and a portable client for workerd and managed Cloudflare Workers.

    🧭 Why Folio

    A Worker, a Linux machine in a Durable Object and a PHP interpreter all end up as one Wasm instance on one thread. Folio spreads the work of that instance across cores without asking the program to be rewritten. The caller passes one ordinary entry point, and the compiler discovers the regions. The task pool, slice pool and chunked recurrences take a caller declaration instead, and the report says which checks each route runs. The same package manages the instance itself: it resets a private instance between jobs, starts a module from a booted heap and refuses memory growth past a cap.

    • Native Sharing. Isolates map the same backing allocation. Four isolates attach to a touched 64 MiB backing for 3.871 MiB of additional resident memory, against 259.930 MiB for copied buffers.
    • Serial Semantics. On the automatic routes, uncertain dependencies run on private overlays and commit in original order. A conflict replays against committed state, and a trap keeps its preceding writes.
    • Original Stack. JSPI suspends the program's own Wasm stack at joins, so branches, scalar carry and host effects behave as they do natively.
    • Instance Control. Checkpoints restore a private instance between jobs, boot images start a module from a booted memory, and the growth governor turns an oversized allocation into a failure the guest can report.
    • Portable. The client and the managed backend use fetch, WebSockets and Durable Objects, with no Node imports and no request-time Wasm compilation.

    Accepted input does not guarantee a speedup. A program with a true serial dependency runs serially, and a small job loses to dispatch overhead.

    📦 Install

    bun add @gmitch215/folio
    # or
    npm install @gmitch215/folio

    The Node backend needs Node 26 or later. Async host imports and the managed backend need WebAssembly JSPI. The browser counted-loop backend works without JSPI, and page-owner transports are portable. Builds from the main branch publish to the snapshot tag.

    🚀 Getting Started

    import { readFileSync } from 'node:fs';
    import { Folio } from '@gmitch215/folio';

    const folio = await Folio.open(readFileSync('./build/fixture.wasm'), { workers: 4 });
    try {
      new Uint32Array(folio.memory.buffer, 1024, 37).fill(1);
      const report = await folio.run('program', [1024, 37, 10000]);
      console.log(report.mode, report.workers, report.regions);
      console.log(folio.inspect('program'));
    } finally {
      await folio.close();
    }

    Folio.open(input, options) accepts a Uint8Array, an ArrayBuffer, a WebAssembly.Module or the result of prepare(bytes). folio.run returns a report that names the mode (serial, speculative or native-shared), the workers that took part and the reason a call stayed serial. A region runs on a worker only when its estimated work pays for dispatch, joining and validation, so a small kernel, a memory-bound loop or a serial recurrence stays at native speed. Getting Started walks through the report and the choice between routes.

    🧩 Examples

    The examples run against the built package with node examples/<name>.ts after bun run build:c and bun run build:

    • basic runs one entry.
    • routing reads the report and shows capped and adaptive routing.
    • iteration runs a loop of per-record calls on workers over a shared memory and compares the digests with the serial run.
    • context-reset resets a private instance between jobs.
    • task-pool joins independent jobs in order.
    • slice-pool fills one shared memory from several threads and audits the run against the serial one.
    • boot-image bakes captured memory into a module.
    • growth-governor caps memory.grow on a guest's memory and shows the guest's failed allocation.
    • continuation runs a guest across alarm events with checkpoints in storage.

    Advanced Usage combines these for specialised cases.

    🗂️ Modules

    Folio has six subpaths. Each one names a runtime boundary or a feature.

    Import Runs on Purpose Page
    @gmitch215/folio Node Folio, the compiler, folds, certificates, the router, task and slice pools, the execution host Core
    @gmitch215/folio/workers Workers and Durable Objects ManagedFolio, FolioLane, the remote client RemoteFolio and the frame and value codecs Workers
    @gmitch215/folio/browser Browsers without JSPI BrowserFolio, which runs one counted-loop call on shared memory Browser
    @gmitch215/folio/memory Portable Page directories and leases, the growth governor and elastic regions Memory
    @gmitch215/folio/boot Portable Boot images: bakeModule, captureImage, applyImage, checkBaked and the image errors Boot
    @gmitch215/folio/continuation Portable Wasm guests across Durable Object alarm events, with page-hash checkpoints in Durable Object SQLite Continuation

    Modules helps choose between them, and Configuration lists every option. Subpaths from 1.1 that are not in this table are no longer exported, and the CHANGELOG lists where each of their names moved. The generated API reference is published to GitHub Pages from bun run docs:build.

    ⚠️ Limits

    Folio keeps the serial result and does not promise a speedup. The automatic routes found no gain on independent library kernels and on three unmodified outside programs, and the explicit routes win where the caller names the independent work. Limits lists what does not parallelize, the gates that were not met and the platform limits, and the technical report holds the figures, the instruments and the raw samples under results.

    🔧 Development

    bun install
    bun run build:c # compile the C fixtures in tests/c with LLVM
    bun run typecheck
    bun run test             # unit gate
    bun run test:integration # local workerd probes and the managed lanes
    bun run build
    bun run example

    Fixtures need clang and wasm-ld with the wasm32 target. Tests need Node 26 for JSPI. bun run test:coverage runs the unit and integration projects with coverage, and bun run test:e2e deploys the probes to a Cloudflare account when FREE_CLOUDFLARE_ACCOUNT_ID and FREE_CLOUDFLARE_API_TOKEN are set. The experiments also accept FOLIO_CLOUDFLARE_ACCOUNT_ID and FOLIO_CLOUDFLARE_API_TOKEN. Layout notes live in tests/, scripts/ and experiments/.

    🤝 Contributing

    Open an issue before a large change. Run bun run typecheck, bun run test and bun run prettier:check before sending a pull request. Changes to the compiler need a differential test against native execution, and a performance claim needs a paired measurement with its raw samples.
